## 2026-09-11 웹 테스트 배포 경로 확정

주소: https://planetracer-daz.pages.dev (Cloudflare Pages, main 브랜치)

main이나 claude/dev에 푸시되면 GitHub Actions가 game-ci로 WebGL을 빌드해 여기에 올린다.
Tifania는 Unity를 켜지 않고 휴대폰으로 이 주소만 연다.

확인한 것 (9/11)
- Unity 6000.3.10f1 도커 이미지가 game-ci에 있다. 첫 빌드 28분, 캐시 이후는 더 짧을 것
- 빌드 결과 14MB. Cloudflare Pages의 파일당 25MiB 제한에 여유가 있다
- Brotli 헤더가 제대로 내려간다. wasm/framework/data 전부 Content-Encoding: br,
  wasm은 Content-Type: application/wasm. web/_headers가 동작한다는 뜻이다

막혔던 곳 두 가지. 같은 실수를 반복하지 않게 적어 둔다.
- wrangler pages deploy는 프로젝트가 없으면 거부한다. 28분 빌드 뒤 마지막 줄에서 막히므로
  생성 단계를 앞에 뒀다 (이미 있으면 에러가 나므로 continue-on-error)
- game-ci는 도커 안에서 root로 빌드해 build/ 가 root 소유로 남는다.
  다음 단계에서 파일 복사조차 Permission denied가 난다. sudo chown 단계가 필요하다

Unity 계정이 구글 연동이어도 id.unity.com에서 비밀번호를 따로 만들면 game-ci가 쓸 수 있다.
비밀번호를 만들어도 구글 로그인은 그대로 된다.

### _headers 규칙은 절대 겹치면 안 된다 (2026-09-11, 첫 배포가 이것 때문에 죽었다)

증상: 화면에 빨간 줄로 "Unable to load file Build/PlanetRacer.framework.js.br".

원인: web/_headers 에 포괄 규칙 `/Build/*.br` 과 확장자별 규칙 `/Build/*.js.br` 을 같이 뒀다.
framework.js.br 에 양쪽이 걸렸고 Cloudflare가 둘을 합쳐 `Content-Encoding: br, br` 로 내려보냈다.
파일은 한 번만 압축돼 있는데 헤더는 두 번이라 말하니, 브라우저가 두 번 풀려다 죽는다.
wasm 과 data 도 똑같이 걸려 있었다.

고친 방법: 포괄 규칙을 없애고 확장자별로 딱 하나씩만 걸리게 했다. no-transform 도 넣었다.

확인 방법: `node tools/check_web_deploy.js`. 브라우저가 하는 일을 그대로 한다 —
br 로 받아 한 번 풀고, 나온 것이 진짜 자바스크립트인지 wasm 매직(\0asm)인지 본다.
워크플로의 "배포 확인" 단계가 이걸 돌리고, 실패하면 빌드를 실패로 만든다.

헤더가 200 인 것만 보고 넘어가면 이 문제를 못 잡는다. 실제로 한 번 놓쳤다.

압축 후 크기 (참고)
- wasm  8.4MB → 푼 것 48MB
- data  5.8MB → 푼 것 15MB
압축을 끄면 wasm 하나가 Cloudflare Pages 의 파일당 25MiB 제한을 훌쩍 넘는다. Brotli는 선택이 아니다.

`web/_headers`·워크플로 설계상 main은 "프로덕션" 브랜치이고(`--production-branch=main`),
claude/dev 푸시는 `--branch=dev`로 별도 프리뷰에 올라간다(`.github/workflows/webgl.yml`).
그런데 **main은 9/11 W-02 이후 커밋이 하나도 없다** — D02-N(밸런스 CSV), W-03(반응형 UI),

주소(`https://planetracer-daz.pages.dev`, main 기준)는 지금도 9/11 상태 그대로다. 게다가 claude/dev
자체도 D02-N 커밋부터 컴파일 오류로 빌드가 안 되고 있었다(아래 daily 9/12 참고, 이번 세션에서 고침) —
즉 지난 며칠 밤·새벽 세션이 "웹에서 확인할 것"에 적어 온 항목들이 실제로는 한 번도 폰 화면에 뜬 적이 없다.

- **A안 — 검증(빌드+테스트) 통과한 커밋은 세션이 곧바로 main에도 fast-forward push**.
  - 좋은 점: 아침 폰 확인이 실제로 최신 진행 상황을 반영한다. 지금처럼 몇 주 치 작업이 안 보이는 일이 없어진다.
  - 대가: 배포 확인 스텝(`tools/check_web_deploy.js`)이 있어서 사이트가 깨진 채로 올라가진 않지만,
    Tifania가 "아직 리뷰 안 한 새 화면"을 매번 봐야 해서 5분 확인이 더 늘 수 있다.
- **B안 — 지금처럼 claude/dev에 계속 쌓고, Tifania가 볼 만하다 싶을 때 수동으로 main에 병합**.
  - 좋은 점: 프로덕션 주소는 그가 원할 때만 바뀐다.
  - 대가: 지금 상황이 반복된다 — daily 파일의 "웹에서 확인할 것"이 몇 주째 무의미해질 수 있다.

    있는 UI가 된다(지금은 접속 중엔 그냥 계속 차오르는 장식일 뿐이다).

    업그레이드/제작 화면을 자주 오가게 만드는 설계 의도라면 오히려 맞을 수도 있다.
- **B안 — 지금처럼 접속 중엔 무제한, 오프라인 캐치업에만 상한.** 화물칸 게이지는 "이 정도

  - 좋은 점: 지금 코드를 안 건드려도 된다. 방치형 특유의 "켜 두면 계속 늘어난다" 느낌이 유지된다.
  - 대가: 화물칸 게이지가 접속 중엔 100%를 넘게 채워질 수 있어(표시는 100%에서 clamp) 사실상
    장식이 된다 — "화물칸"이라는 자원이 실제로는 오프라인 상황에서만 의미가 있다는 게 직관적이지 않다.

  것 — **채굴차 부품**이 주 보상으로 들어간다"(L-03 결정 당시 GDD를 뒤집은 부분). 채굴차 부품은
  `RigPartReward`(Tool/Cargo/Engine/Detector/Refinery 슬롯 레벨업)이고 등급 개념이 아직 없다 —
  지금은 `RigPartApply.LevelBonus`가 전부 +1 고정(P4에서 등급별 차등 예정, decisions.md 위쪽 항목들 참고 안 함, core-loop.md "아직 안 정한 것" 참고).

두 문서를 그대로 합치면 "공구 상자 등급이 낮으면(C/B) 채굴차 부품 슬롯을 올려 주고, 높으면(A/S)
레이싱카 부품 청사진(제작 없이 바로 보유)을 준다"는 절충이 자연스러워 보이지만, 이건 추측이지
결정이 아니다. 선택지:

- **A안 — 등급 전부 채굴차 부품(RigPartReward)으로 통일.** 등급은 슬롯을 무작위로 고르는 데만
  쓰거나(C=아무 슬롯, S=희귀 슬롯인 Detector/Refinery 우대 등) LevelBonus 크기에 반영한다.
  - 좋은 점: core-loop.md의 "채굴차 부품이 주 보상" 원칙과 완전히 일치, RigPartApply 상한 클램프
    로직을 그대로 재사용할 수 있다.
  - 대가: GDD의 "청사진" 표현과 어긋난다 — 문서를 하나 더 고쳐야 한다.
- **B안 — 등급 C/B는 채굴차 부품, A/S는 레이싱카 부품 청사진(제작 비용 없이 즉시 보유).** GDD의
  "청사진" 표현을 살리면서 core-loop.md의 "주 보상은 채굴차 부품" 원칙도 지킨다(A/S는 드물게만
  나오니 "주 보상"은 여전히 C/B의 채굴차 부품 쪽).
  - 좋은 점: 두 문서를 다 살릴 수 있다. 레이싱카 부품에 등급이 이미 있어서(PartGrade) LootResult.Grade와
    자연스럽게 맞는다.
  - 대가: 지금 B/A/S 등급 레이싱카 부품 정의 자체가 `DefaultData`에 없다(C만 있음, `PartCraft.Cost`도
    C만 정의) — 이 안을 고르면 그 정의부터 먼저 만들어야 한다. 상자별로 두 가지 보상 종류를 분기하는
    로직도 새로 생긴다.
- **C안 — 지금 당장은 정하지 않고, LootTable을 등급만 뽑는 순수 확률 엔진으로 남겨 둔다(이번 세션이 한 것).**
  개봉 연출·인벤토리 반영(D11-N 나머지)과 실제 보상 매핑은 A/B안 중 하나가 정해진 뒤로 미룬다.
  - 좋은 점: 결정 없이도 확률표·천장·분포 테스트(D11-M)는 완성해 둘 수 있다 — 되돌릴 일이 없다.
  - 대가: D11-N이 완전히 끝난 게 아니다. 개봉 화면·상자 인벤토리(SaveData 필드)는 다음 세션 몫으로 남는다.

### T-08. 로컬 레이스 우승 보상 — 확정 슬롯(L-03)과 GDD의 "녹슨 상자" 둘 다 줄지

D11-N 이어가는 중 또 하나 어긋나는 부분을 발견했다. `docs/GDD.md` "레이스" 항목은 "로컬 5(연료1,
녹슨 상자) / 서킷 3(강철) / 챌린지 1(티타늄)"이라고 등급별 상자만 보상으로 적어 뒀는데, L-03
결정으로 쿼츠 로컬 레이스 3개는 코스마다 고정된 `RigPartReward`(Tool/Cargo/Engine 슬롯을 하나씩
확정으로 올려 줌, 온보딩 예측 가능성 때문)를 이미 주고 있다 — GDD의 상자 보상은 코드 어디에도
반영된 적이 없었다.

**결정: 둘 다 준다.** 확정 슬롯 보상은 그대로 두고(되돌릴 이유가 없다 — 온보딩 설계 의도가
분명하다), 추가로 GDD대로 코스 등급(`RaceTier`)에 맞는 상자를 얹는다. `Core/RaceSimulator.cs`의
`Course`에 `Tier` 필드(Local/Circuit/Challenge/GrandPrix, 그랑프리는 상자가 아니라 GDD의
"워프"라 매핑에서 제외)를 추가하고, `Core/RaceBoxReward.cs`(로컬=녹슨/서킷=강철/챌린지=티타늄)로
매핑, `MiningController.TryEnterRace`가 우승 시 `_save`의 상자 개수 필드에 바로 더하도록 배선했다.
서킷·챌린지 코스 자체(트랙 데이터·해금 구조)는 만들지 않았다 — `docs/backlog.md` W2("레이스
4등급 해금 구조")가 이미 예정해 둔 일이라 여기서 앞서가지 않았다. 지금은 쿼츠 로컬 레이스 3개가
전부 `Tier = Local`이라 실제로는 녹슨 상자만 나온다.
