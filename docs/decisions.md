## 2026-09-11 웹 테스트 배포 경로 확정

주소: https://planetracer-daz.pages.dev (Cloudflare Pages, main 브랜치)

main이나 claude/dev에 푸시되면 GitHub Actions가 game-ci로 WebGL을 빌드해 여기에 올린다.
Tifania는 Unity를 켜지 않고 휴대폰으로 이 주소만 연다.

확인한 것 (9/11)
- Unity 6000.3.10f1 도커 이미지가 game-ci에 있다. 첫 빌드 28분, 캐시 이후는 더 짧을 것
- 빌드 결과 14MB. Cloudflare Pages의 파일당 25MiB 제한에 여유가 있다
- Brotli 헤더가 제대로 내려간다. wasm/framework/data 전부 Content-Encoding: br,
  wasm은 Content-Type: application/wasm. web/_headers가 동작한다는 뜻이다

막혔던 곳 두 가지. 같은 실수를 반복하지 않게 적어 둔다.
- wrangler pages deploy는 프로젝트가 없으면 거부한다. 28분 빌드 뒤 마지막 줄에서 막히므로
  생성 단계를 앞에 뒀다 (이미 있으면 에러가 나므로 continue-on-error)
- game-ci는 도커 안에서 root로 빌드해 build/ 가 root 소유로 남는다.
  다음 단계에서 파일 복사조차 Permission denied가 난다. sudo chown 단계가 필요하다

Unity 계정이 구글 연동이어도 id.unity.com에서 비밀번호를 따로 만들면 game-ci가 쓸 수 있다.
비밀번호를 만들어도 구글 로그인은 그대로 된다.

### _headers 규칙은 절대 겹치면 안 된다 (2026-09-11, 첫 배포가 이것 때문에 죽었다)

증상: 화면에 빨간 줄로 "Unable to load file Build/PlanetRacer.framework.js.br".

원인: web/_headers 에 포괄 규칙 `/Build/*.br` 과 확장자별 규칙 `/Build/*.js.br` 을 같이 뒀다.
framework.js.br 에 양쪽이 걸렸고 Cloudflare가 둘을 합쳐 `Content-Encoding: br, br` 로 내려보냈다.
파일은 한 번만 압축돼 있는데 헤더는 두 번이라 말하니, 브라우저가 두 번 풀려다 죽는다.
wasm 과 data 도 똑같이 걸려 있었다.

고친 방법: 포괄 규칙을 없애고 확장자별로 딱 하나씩만 걸리게 했다. no-transform 도 넣었다.

확인 방법: `node tools/check_web_deploy.js`. 브라우저가 하는 일을 그대로 한다 —
br 로 받아 한 번 풀고, 나온 것이 진짜 자바스크립트인지 wasm 매직(\0asm)인지 본다.
워크플로의 "배포 확인" 단계가 이걸 돌리고, 실패하면 빌드를 실패로 만든다.

헤더가 200 인 것만 보고 넘어가면 이 문제를 못 잡는다. 실제로 한 번 놓쳤다.

압축 후 크기 (참고)
- wasm  8.4MB → 푼 것 48MB
- data  5.8MB → 푼 것 15MB
압축을 끄면 wasm 하나가 Cloudflare Pages 의 파일당 25MiB 제한을 훌쩍 넘는다. Brotli는 선택이 아니다.

### T-06. 화물칸 상한을 접속 중(온라인)에도 적용할지

지금 `MiningSimulator.Offline`(오프라인 캐치업)은 화물칸 상한(`CargoHours`)에서 산출을 자른다.
하지만 `MiningController.Update()`(접속해서 실시간으로 보는 동안)는 상한 없이 원석이 계속 쌓인다 —
즉 방치 후 돌아왔을 때만 "화물칸이 다 찼다"는 벌칙이 있고, 화면을 보면서 채굴 중일 때는 무제한이다.
이번 세션에서 HUD에 화물칸 게이지를 붙이면서 발견했다(`MiningController.CargoCapacityMinerals`).

- **A안 — 접속 중에도 상한에서 멈춘다.** 게이지가 꽉 차면 원석이 더 안 쌓이고, 정제(제련)나
  업그레이드로 비워야 다시 쌓인다.
  - 좋은 점: "화물칸을 관리해야 한다"는 압박이 항상 일관되게 작동한다. 게이지가 실제로 의미
    있는 UI가 된다(지금은 접속 중엔 그냥 계속 차오르는 장식일 뿐이다).
  - 대가: 접속 중에도 계속 지켜보며 비워야 해서 방치형의 "그냥 켜 두면 된다" 느낌이 줄어든다.
    업그레이드/제작 화면을 자주 오가게 만드는 설계 의도라면 오히려 맞을 수도 있다.

`image-session.md` 3절은 "`check_alpha.py`를 통과(exit 0)해야만 커밋한다"인데,
`check_alpha.py`는 **투명 PNG 전용**이다(모드가 RGBA가 아니면 그 자리에서 실패).
컷신은 `art-requests.md`에 **"배경 제거 안 함. 그대로 쓴다"**(남색 배경 16:9)라고 적혀 있다.
**불투명 그림은 설계상 통과가 불가능하다 — 그림 품질 문제가 아니다.**
규칙 두 개가 서로 어긋나 있는 것이고, 어느 쪽을 고칠지는 세션이 혼자 정할 일이 아니다.

- **A안 — `check_alpha.py`에 `--opaque` 모드를 넣는다.** 그 모드에서는 알파·모서리·투명 비율을
  건너뛰고 "열리는가 / 크기가 요청 이상인가 / 마젠타 잔상이 없는가"만 본다.
  검사가 계속 살아 있고, 아이콘 쪽 기준도 그대로 남는다.
- **B안 — `image-session.md` 3절에 "장부 참고가 `배경 제거 안 함`인 항목은 투명 검사 대상이
  아니다"를 한 줄 명시한다.** 코드를 안 건드리는 가장 작은 수정. 대신 컷신에는 자동 검사가
  아예 없어진다.
- **C안 — 컷신도 투명 배경으로 받는다**(장부의 "배경 제거 안 함"을 뒤집는다).
  7장을 버리고 다시 뽑아야 하고, 배경이 컷신 분위기의 대부분이라 그림이 크게 달라진다.

추천은 **A안**이다. B안과 결과는 같은데 검사가 남고, 아래 "크기" 문제도 같은 곳에서 잡힌다.
A·B 어느 쪽이든 **디스크의 7장을 그대로 커밋**하면 끝난다(다시 뽑을 필요 없음).

### 곁들여 — 장부의 크기 표기가 틀렸다

`art-requests.md`는 `16:9 (1536x1024 이상)`이라고 적고 있는데 **1536x1024는 3:2다.**
실제로 온 그림은 **1672x941**로, 비율은 1.777 — 정확히 16:9다. 가로는 요청을 넘고
세로만 모자란 것처럼 보이는 건 표기가 애초에 어긋나 있어서다.
**크기 자체는 충분하다**: 이 게임 기준 해상도는 540x960 세로(`BootstrapMainGame.cs` 등)라
16:9 가로 그림을 레터박스로 깔면 폭 540px면 된다 — 1672는 그 3배다.
표기를 `16:9 (1600x900 이상)`으로 고치면 실물과 맞는다.
