### W-08 — 배포 확인 스텝이 엉뚱한 주소를 확인하고 있던 문제 (계획에 없었지만 발견해서 바로 고침)

L-04/D04-N을 push한 뒤 이번 빌드가 실제로 잘 도는지 GitHub Actions로 지켜보다가(`actions_list`로
run #14 확인), `.github/workflows/webgl.yml`의 "배포 확인" 스텝이 `node tools/check_web_deploy.js`를
**인자 없이** 부르고 있는 걸 발견했다. `check_web_deploy.js`의 기본값은 main 기준 프로덕션 주소
(`https://planetracer-daz.pages.dev`)라서, claude/dev로 push한 날도 이 스텝은 항상 그 주소만 확인해
왔다는 뜻이다. `pages deploy --branch=dev`는 프로덕션 별칭을 안 바꾸니(별도 프리뷰 주소로 올라간다),
지금까지 claude/dev push에서 뜬 "배포 확인 성공"은 그날 새로 올린 dev 빌드가 아니라 예전에 성공했던
main 내용을 다시 확인한 것뿐이었다 — W-07(빌드 자체가 깨져 있던 것)과는 다른, "빌드는 통과해도 진짜
확인은 안 하고 있었다"는 더 근본적인 구멍이다.

- 고친 방법: 배포 스텝에 `id: deploy`를 주고, `steps.deploy.outputs.deployment-url`(없으면
  `pages-deployment-alias-url`)을 `check_web_deploy.js`에 넘기게 했다. `cloudflare/wrangler-action@v3`가
  `pages deploy` 실행 후 이 이름으로 배포 URL을 출력한다고 알고 있는데, 실제로 이 이름이 맞는지는
  이번 push로 도는 빌드(run #14) 로그에서 다음 세션이 확인해야 한다 — 이름이 틀려도 빈 문자열이 되어
  기존 기본값(main 주소)으로 조용히 넘어가니 최소한 지금보다 나빠지지는 않는다(하위 호환).
- `check_web_deploy.js` 맨 앞에 `대상: <url>` 로그 줄을 추가해서, Actions 로그만 보고도 이번에
  실제로 어느 주소를 확인했는지 바로 알 수 있게 했다.
- **확인 완료.** push 후 run #14는 concurrency 그룹 때문에 취소되고(같은 브랜치에 바로 다음 커밋을
  올려서) run #15로 합쳐 돌았다. 로그 확인 결과 `deployment-url` 출력이 실제로 존재했고, "배포 확인"
